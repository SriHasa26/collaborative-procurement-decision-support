# Phase 3A.3 — Historical Data Source Strategy

**Date of investigation:** 2026-09-13
**Scope:** Determine the best reliable source for acquiring sufficient real historical mandi price data (Tomato, Onion, Potato — Telangana) for the ML trend-classification component selected in Phase 3A.1.
**Rule followed throughout:** no endpoint was guessed, no data point was fabricated or simulated, and no anti-automation control (CAPTCHA, login gate) was worked around. Every claim is either a direct, reproducible HTTP result or explicitly marked as an inference/assumption.
**Reproducibility:** every result below can be regenerated by running `scripts/phase3a2_ceda_data_probe.py` (CEDA) and `scripts/phase3a3_official_agmarknet_probe.py` (official Agmarknet 2.0) from the project root.

---

## 1. Objective

Phase 3A.2 established that data.gov.in's "current daily price" dataset is a same-day snapshot, and that CEDA's Agri-Market Data portal returns real daily historical prices but does so unreliably. This phase's objective is narrower and more decisive than re-testing CEDA further: **define what "enough data" actually means for the ML component, investigate whether the official Agmarknet source can do better, compare it against CEDA on evidence, and commit to a primary and fallback source before any acquisition work begins.**

## 3. Minimum ML Data Requirements

Before touching any source, the minimum acceptable dataset is defined here, in advance, so source selection is not driven by "whichever source is easiest today":

| Requirement | Minimum acceptable | Rationale |
|---|---|---|
| **Commodities** | Tomato and Potato at minimum; Onion desirable but not blocking | Matches Phase 1B/1C/3A.1's already-fixed commodity scope. Onion is not dropped from the project — see Section 10 — but a source that only delivers 2 of 3 commodities reliably is still usable for a reduced-but-real ML component, whereas a source that delivers 0 commodities reliably is not. |
| **Granularity** | Daily records | Phase 3A.1's trend-classification target is explicitly short-horizon (3-day); monthly aggregates cannot support this (Phase 3A.1, Section 7.4). |
| **Chronology** | Records must be genuinely dated and non-duplicated, one row per commodity-market-day (or a clearly documented aggregation level) | A model trained on unordered or duplicated rows would silently violate the mandatory chronological train/test split (Phase 3A.1, Section 7.5). |
| **Location** | At minimum, district-level; market-level (Bowenpally/Gaddiannaram specifically) preferred | Phase 3A.1, Section 7.2 already fixed the geographic scope to these two Hyderabad mandis; a source that cannot resolve to at least district level reintroduces a scoping question this project already closed. |
| **Minimum span per series** | At least 90 continuous days for a first usable model; 6–12 months preferred for a credible chronological train/test split | Below ~90 days there is not enough history for a meaningful walk-forward validation window (Phase 3A.1, Section 7.5); this is a floor, not a target. |
| **Missing-data tolerance** | Occasional single-day gaps acceptable if documented; a source that cannot demonstrate at least one continuous multi-week stretch is not acceptable | Phase 3A.1, Section 19 already anticipates gap-checking as a required preprocessing step, not an unexpected obstacle. |
| **Reproducibility** | The exact same request must be re-runnable by a script and produce comparable results (not necessarily byte-identical, since prices are naturally revised/updated) | This project's own discipline (Phase 1B: verify against primary sources, don't trust once) requires this be automatable, not a one-off manual copy-paste that can't be audited or redone. |
| **Price units** | ₹ per quintal (or ₹ per unit clearly stated), with min/max/modal (or clearly documented equivalent) distinguished | Matches the field structure already used in Phase 1B/1C's wholesale price figures — a source using undocumented or inconsistent units would break comparability with existing project numbers. |
| **Legitimacy** | Official government source, or a source that itself republishes official government data with a stated, checkable provenance | Consistent with this project's standing rule (Phase 1B) against uncritically trusting secondary aggregators after the 2–3× price-disagreement finding. |

**A source is "acceptable" for Phase 3A.4 if it can reproducibly satisfy the granularity, chronology, and minimum-span rows above for at least Tomato and Potato.** It does not need to satisfy all three commodities equally well on day one — that would be an artificial bar not required by Phase 3A.1's own design (which already treats the three-commodity, two-mandi scope as the target, not necessarily a simultaneous first success for all six series).

## 4. Candidate Source Investigation

### 4a. CEDA Agri-Market Data (`agmarknet.ceda.ashoka.edu.in`)
Already investigated in depth in Phase 3A.2 (Section 3–6 there). Not re-derived here; see Section 2 above and Section 5 for a fresh confirmatory check.

### 4b. Official Agmarknet 2.0 (`agmarknet.gov.in` / `api.agmarknet.gov.in`)

**No API was assumed to exist.** The same method used on CEDA in Phase 3A.2 was applied here: the portal's homepage was fetched and found to be a React single-page app serving one minified JS bundle (`/static/js/main.9bdd0f6c.js`, ~1.1 MB). That bundle was downloaded and searched as plain text for its axios `baseURL` and for `.get("...")`/`.post("...")` call sites — this is how every endpoint below was found, not guessed.

**Endpoints confirmed to exist** (base `https://api.agmarknet.gov.in/v1`):

| Endpoint | Method | Purpose | Result when tested |
|---|---|---|---|
| `/daily-price-arrival/filters` | GET | Reference data: states, districts, markets, commodities, grades, varieties, **and the officially documented allowed date range per report type** | 🟢 Open, fast (0.7s), returned real data |
| `/daily-price-arrival/report` | POST | The actual price/arrival report (what the UI's "Price and Arrival Report" screen calls) | 🔴 Blocked — requires CAPTCHA (Section 4c) |
| `/prices-and-arrivals/market-report/daily` | POST | A market-level daily report | 🔴 Returned a generic server error (500) on a first-pass field-name guess; not pursued further once the CAPTCHA gate was confirmed on the sibling endpoint below, since the gate is the decisive finding, not this endpoint's exact schema |
| `/prices-and-arrivals/commodity-market/daily-report-weighted` | POST | A weighted daily commodity/market report | 🔴 Blocked — requires CAPTCHA (same gate) |

**Historical range — a genuine, documented finding, not an estimate.** The `/daily-price-arrival/filters` response includes a `range_data` object stating, in the government portal's own words:

```json
"price": {"from_date": "2021-01-01", "to_date": "2026-09-13", "allowed_year_range": 1}
```

i.e. the "Price" report type officially covers **2021-01-01 through today**, with a **maximum 1-year window per single query** (so a multi-year pull would require several sequential requests, not one). This is a materially longer documented range than anything CEDA's UI or API disclosed in Phase 3A.2. A separate combined "Price + Arrival" report type is explicitly limited to 2025-11-07 onward ("Agmarknet 2.0 go-live date") — the price-only report is the one relevant here, and it is not subject to that shorter cutoff.

**Reference data directly matches this project's existing scope — a genuine, unplanned confirmation:**
- Telangana → `state_id = 32`
- Tomato → `cmdt_id = 65`; Onion → `cmdt_id = 23`; Potato → `cmdt_id = 24`
- Hyderabad → `district_id = 566`
- **Bowenpally APMC → `market_id = 1868`** and **Gaddiannaram APMC → `market_id = 377`** — both found by name in the live market list. These are the exact two mandis Phase 1B/1C already fixed as this project's study sites. This was not searched for opportunistically to make the source look better — it is simply what the reference data contains, and it is a meaningful point in this source's favor if it becomes usable.

### 4c. The CAPTCHA Gate — Confirmed, Not Bypassed

Every report-generating endpoint tested rejected an unauthenticated POST request with an identical, explicit error:

```json
{"detail":"Captcha key and captcha value are required.","code":"TOKEN_OR_CAPTCHA_REQUIRED"}
```

This is a real HTTP 400 response from a real backend, not a network failure — the server understood the request's fields (it did not complain about unknown parameters) and specifically demanded a solved CAPTCHA before returning any data. The bundle also contains a full CAPTCHA flow (`/captcha/generator`, `/captcha/verify`, `/captcha/getaudio/`) tied to a mobile-OTP guest-login system.

**This project does not attempt to solve, automate, or route around this control.** It is a deliberate anti-bot measure on a government system, and bypassing it would fall outside what this project is willing to do, independent of whether it would be technically possible. This is treated as a hard, permanent constraint on this endpoint for automated use, not a temporary obstacle.

## 8. Primary Source Decision

**Primary source: CEDA Agri-Market Data.**

This is not the "easier" choice by convenience — it is the only one of the two that has ever actually returned a real, verifiable price record to an automated request. The official government portal's own data is, on paper, more historically extensive and more precisely located (Section 7), and that documentation is itself valuable (Section 9) — but "documented to exist" and "acquirable" are different claims, and only CEDA has satisfied the second one so far. Selecting the official portal as primary today would mean designing an acquisition pipeline around a source that has not yet delivered a single data point, which is not a decision this project's own evidentiary standard (Phase 1B, Phase 3A.1) permits.

This decision is explicitly conditional, not final: if CEDA's reliability does not improve enough to support a real bulk pull in Phase 3A.4 (Section 9's acquisition plan includes a concrete reliability checkpoint for exactly this reason), this designation should be revisited — not defended past the evidence.

## 9. Fallback Source Decision

**Fallback source: Official Agmarknet 2.0, via manual (human-in-the-loop) report export — not automated API access.**

The CAPTCHA gate blocks *scripted* access, but does not block a person using the portal's own web UI: a human can select the same filters this report has already confirmed exist (Telangana, Bowenpally/Gaddiannaram, Tomato/Onion/Potato, a date range within the documented 2021-01-01–present window), solve the CAPTCHA once, and use the UI's own "download report" feature (confirmed present in the bundle as a `responseType: "blob"` download action) to obtain a CSV/Excel export. This is slower and not scriptable, but it is honest, real, and — critically — backed by better-documented historical depth than CEDA has shown. It is named as a fallback, not the primary, specifically because it requires manual effort per acquisition batch, which this report does not treat as free.

**Not selected even as a fallback:** data.gov.in's other Agmarknet-derived resources (e.g., "Variety-wise Daily Market Prices Data of Commodity," listed in Phase 3A.1's sources). This report attempted to inspect it and found it, too, is a JavaScript-rendered page that does not expose its underlying resource ID or data structure without a registered data.gov.in API key (which this project does not hold, per Phase 3A.1, Section 6). Given that data.gov.in's sibling "Current Daily Price" resource was already confirmed in Phase 3A.2 to be a same-day snapshot rather than a historical archive, and that this project's established pattern (Phase 1B) is not to trust an unverified secondary claim, this resource is **not recommended for further pursuit** unless CEDA and the official-portal fallback both fail — this is stated as an inference pending verification, not a confirmed rejection, since it was not actually tested against a real API key.

## 10. Historical Data Acquisition Plan (for Phase 3A.4)

This section defines the plan; it is not executed in this phase.

1. **Primary commodity/commodities:** Tomato and Potato first (both have a confirmed successful CEDA retrieval already). Onion is attempted in parallel but is explicitly allowed to fail without blocking the other two — Phase 3A.4 should not be gated on solving Onion's 7/7 CEDA failure rate.
2. **Geographic level:** District level (Hyderabad), matching what CEDA's `/api/prices` actually returns per record. If the official-portal fallback is used instead, its market-level granularity (Bowenpally/Gaddiannaram specifically) should be preferred, since it is finer and matches Phase 1B/1C's original mandi-level scope more precisely.
3. **Historical time range to acquire:** Start with a 90-day continuous window (this report's Section 3 floor) via CEDA; if that succeeds and the backend seems stable that session, extend incrementally (e.g., in 90-day increments) toward 6–12 months rather than requesting a full year in one call, given the timeout pattern observed on even 7-day and 30-day CEDA requests in Phase 3A.2.
4. **Required fields:** date, commodity, district (or market), `p_min`, `p_max`, `p_modal` (or the official portal's equivalent fields, if the fallback is used) — matching what has already been structurally verified in Section 5/Phase 3A.2.
5. **Acquisition method:** Scripted, retried HTTP requests against CEDA's `/api/prices` (extending `scripts/phase3a2_ceda_data_probe.py`'s pattern — small windows, explicit retry counts, no silent fallback to fabricated data on failure). Each request's outcome (success/500/504) must be logged, not just its successes.
6. **Expected file format:** Raw JSON responses saved unmodified (as this phase and Phase 3A.2 already do), with a separate, clearly-labeled processing step (not part of acquisition) to flatten them into a CSV/dataframe for modeling.
7. **Raw data storage location:** `data/raw/ceda/` for CEDA pulls (continuing the existing convention), `data/raw/agmarknet_official/` for any manually-exported fallback files, each named with commodity, market/district, and date range, exactly as done in this phase and Phase 3A.2.
8. **Retry/fallback strategy:** Per-request retries (3 attempts, as already implemented in both probe scripts) before marking a specific commodity/date-window as failed; if CEDA's overall success rate over a real 90-day pull attempt is too low to assemble a usable series (a threshold Phase 3A.4 should define numerically before starting, not after), fall back to a manual official-portal export for the specific commodity/mandi combinations that failed, rather than substituting synthetic data.

## 11. Risks and Limitations

- **CEDA's reliability could degrade further, or improve** — today's evidence (Section 5) is a snapshot of this specific day's backend behavior, not a permanent SLA. Phase 3A.4 must re-check reliability at the start of the actual pull, not assume today's pattern holds indefinitely.
- **A 90-day or longer CEDA pull has never actually been attempted successfully** — every multi-day window tested so far (in this phase and Phase 3A.2) was 7 or 30 days, and the 30-day Onion attempt in Phase 3A.2 timed out. There is a real, undemonstrated risk that longer windows fail more often, not less.
- **The official portal's documented 2021–2026 range is a claim from its own filters metadata, not a range this report has verified by successfully retrieving records from it** — it is trustworthy as an official government statement about its own system, but it remains unverified by direct data retrieval, and is reported as such (Section 4b), not conflated with a confirmed data pull.
- **Onion may simply not be acquirable from CEDA** — 7/7 failures across two phases and multiple query shapes (daily, monthly, district- and state-level) is a strong, specific signal, not sampling noise. Phase 3A.4 should plan for a two-commodity ML component (Tomato, Potato) as the realistic baseline, with Onion as a stretch goal, not a requirement.
- **The manual fallback does not scale** — it depends on a person solving a CAPTCHA and clicking through the UI per export, which is fine for a one-time or occasional supplementary pull but is not a repeatable pipeline. It should not be relied on as the primary mechanism for ongoing or large acquisitions.

## 12. Final Verdict

**CEDA Agri-Market Data is designated the primary source, and manual export from official Agmarknet 2.0 is designated the fallback, based strictly on what each source has actually been observed to do, not on which is officially more authoritative.** The official portal is, on paper, the better-documented and better-located source — its own reference data confirms a longer historical range and resolves down to this project's exact study mandis — but it has not yet yielded a single retrievable price record to an automated request, and by deliberate design (a CAPTCHA gate this project will not circumvent) it may never do so without human involvement. CEDA, despite its unreliability, is the only source that has actually produced real, verifiable daily price data for this project's target commodities. This is a "promising but requires correction" verdict for CEDA (echoing Phase 3A.1's own verdict language) and a "documented but currently inaccessible" verdict for the official portal — neither a clean win, and both stated as such rather than rounded up.
