# Phase 4A — Low-Complexity ML Model Evaluation

**Date:** 2026-09-13
**Scope:** Fit exactly three low-complexity model families (Linear Regression, Ridge Regression, Decision Tree Regressor) through the Phase 3A.9 expanding-window protocol, and determine honestly whether any of them adds value over the moving-average-3 baseline (mean MAE 189.84). No Random Forest, XGBoost, LightGBM, CatBoost, neural network, or LSTM was used. The 35-row final test set was not evaluated.
**Rule followed throughout:** every number below comes from actually running `scripts/phase4a_low_complexity_models.py`. No raw file, no processed dataset, and no prior report was modified.
**Reproducibility:** every result can be regenerated by running `scripts/phase4a_low_complexity_models.py` from the project root (`random_state=42` is fixed for Ridge and Decision Tree wherever randomness could otherwise apply, for exact reproducibility).

---

## 1. Phase Objective

Phase 3A.9 established that the moving-average-3 baseline (mean validation MAE 189.84) already beats naive persistence (241.43). This phase's job is to test — not assume — whether a small set of genuinely low-complexity ML models can do better than that stronger baseline, using the identical chronological split, the identical 5-fold expanding-window protocol, and the identical common 175-row evaluation window Phase 3A.9 defined. The purpose is to find out whether ML adds value, not to manufacture a result that says it does.

## 3. Candidate Model Rationale

Exactly three model families were evaluated, per the task's explicit list — no others were introduced.

| Model | Why appropriate here |
|---|---|
| **Linear Regression** | The simplest possible model that can use more than one feature at once; fully interpretable (each coefficient has a direct, readable meaning); a natural reference point for "does a straight-line relationship between recent prices and the next one explain anything." |
| **Ridge Regression** | Adds L2 regularization on top of Linear Regression — directly relevant given Phase 3A.8's own finding that individual lag features correlate weakly with the target (Section 4 there): regularization is the standard, low-complexity tool for controlling coefficient magnitude when predictors are only weakly informative, which is exactly this dataset's situation. |
| **Decision Tree Regressor (shallow)** | The simplest model family that can capture a *non-linear* or threshold-based relationship (e.g., "if the recent price is above ₹X, the next price tends to behave differently") — included specifically to check whether the weak *linear* correlations found in Phase 3A.8 might be hiding a non-linear pattern a straight line cannot see. Depth is restricted (max_depth ∈ {2,3,4}) precisely because an unrestricted tree on ~105–133 training rows would trivially memorize the training data. |

All three are standard, well-understood, low-parameter-count models appropriate for a 105–133-row training window — none requires anywhere near this dataset's size to fit reliably, which is exactly why they were chosen over anything heavier.

## 4. Model Configurations

No broad search was run. The complete, exhaustive list of configurations actually evaluated:

| Model | Configurations |
|---|---|
| Linear Regression | 1 (default, no hyperparameters) |
| Ridge Regression | 3: `alpha ∈ {0.1, 1.0, 10.0}` |
| Decision Tree Regressor | 3: `max_depth ∈ {2, 3, 4}` |

Each of these 7 configurations was run against **both** feature sets (minimal, extended) — 14 total model runs, each evaluated across the identical 5 expanding-window folds. This is the complete set; nothing was tried and omitted from this report.

## 5. Scaling Policy

| Model | Scaled? | Reasoning |
|---|---|---|
| Linear Regression | Yes (applied, though not strictly required for prediction correctness — OLS predictions are scale-invariant; scaling was applied anyway for numerical stability and to keep the pipeline identical across all three linear/regularized models) | `StandardScaler` |
| Ridge Regression | **Yes, required** | Ridge's L2 penalty is applied to raw coefficient magnitudes, which are scale-dependent — an unscaled feature with a naturally large numeric range (e.g., a price in the thousands) would be penalized differently than one with a small range (e.g., a 0/1 day-of-week dummy) purely due to units, not real importance. Scaling removes that artifact. |
| Decision Tree Regressor | **No** | Tree splits are threshold comparisons on one feature at a time and are invariant to monotonic rescaling — scaling would change nothing about the fitted tree's structure or predictions. |

**Implementation, verified in code, not just described:** for every fold, `StandardScaler().fit(X_train)` is called using **only that fold's training rows** — never the validation rows, and never the full 175-row dataset. The fitted scaler's `.transform()` (never `.fit_transform()` or a second `.fit()`) is then applied to that fold's validation rows. This means fold 2's scaler (fit on rows [0:112]) is different from fold 1's scaler (fit on rows [0:105]) — each fold gets its own correctly-scoped scaler, consistent with the expanding-window design.

## 6. Validation Protocol

Reused exactly from Phase 3A.9, not redefined: common window = 175 rows; split = train [0:105] / validation [105:140] / test [140:175]; 5 expanding-window folds of 7 validation rows each (train ranges 105→112→119→126→133). **The test partition's boundaries were computed and printed by this script, but rows [140:175] were never passed into any `.fit()` or `.predict()` call** — confirmed directly by inspecting the script's control flow, not merely asserted.

## 10. Minimal vs Extended Comparison

**Best minimal-set result:** Ridge (α=10.0), mean MAE 168.46.
**Best extended-set result:** Ridge (α=1.0), mean MAE 147.52.

**Extended beats minimal by roughly 21 MAE points (≈12% relative) at their respective best configurations.** This gap is consistent across model families (extended's Linear Regression, Ridge, and depth-2 tree all outperform their minimal counterparts), not an artifact of one favorable comparison. The most plausible explanation, grounded in Phase 3A.8's own correlation findings: `lag_3` (correlation 0.218 with the target) and `rolling_mean_3` carry more real signal than `lag_1` alone (correlation 0.049), so a model with access to them has genuinely more to work with — this is consistent with, not contradicted by, the mean-reversion mechanism described in Section 13.

**Both feature sets were compared on the identical common-window folds** (Section 6) — no comparison in this report pits one feature set's performance on one set of target observations against the other's performance on a different set.

## 11. Overfitting Analysis

**Decision Trees show clear, worsening overfitting as depth increases — reported honestly, not minimized:**

| Feature set | Depth | Train MAE | Val MAE | Gap |
|---|---|---|---|---|
| minimal | 2 | 144.79 | 180.06 | +35.27 |
| minimal | 3 | 139.99 | 186.80 | +46.81 |
| minimal | 4 | 134.41 | 181.91 | +47.50 |
| extended | 2 | 136.35 | 168.14 | +31.79 |
| extended | 3 | 120.90 | 168.94 | +48.04 |
| extended | 4 | 102.98 | 175.48 | **+72.50** |

**The pattern is unambiguous: as `max_depth` increases, training MAE keeps falling (the tree fits its training data increasingly well) while validation MAE does not improve correspondingly — for the extended set it actually gets *worse* from depth 2 (168.14) to depth 4 (175.48).** This is textbook overfitting: a more complex tree memorizes training-set noise that does not generalize to the next fold's data. **The shallowest tree tested (depth=2) is the best-performing tree in both feature sets** — a direct, data-backed argument for keeping tree complexity low on a dataset this size, not merely a generic caution repeated from the task instructions.

**Linear Regression and Ridge show a much smaller, more stable train-val gap** (+8 to +11 across all configurations) — consistent with their lower effective complexity (few or no free hyperparameters, and regularization actively shrinking Ridge's coefficients further as alpha increases, shown by the shrinking gap from α=0.1 to α=10.0 in both feature sets).

## 12. Model Selection

**Provisional best model, using validation data only, per the task's stated priority order:**

1. **Lowest mean MAE:** extended / Ridge (α=1.0) — 147.52.
2. **Stability across folds:** its stdev (56.66) is the lowest among the top-4 extended linear configurations (56.88, 56.86, 56.66, 55.42 for LR, Ridge-0.1, Ridge-1.0, Ridge-10.0 respectively) — essentially tied with Ridge(α=10.0)'s stdev (55.42), which has a marginally higher mean MAE (147.77) and marginally lower mean RMSE (190.87 vs. 192.85).
3. **RMSE:** Ridge(α=1.0)'s RMSE (192.85) is close to but not the lowest among its near-tied peers (Ridge α=10.0 achieves 190.87) — a minor, not decisive, difference.
4. **Simplicity:** among the four near-identical top configurations (LR, Ridge-0.1, Ridge-1.0, Ridge-10.0), plain Linear Regression is the simplest (zero hyperparameters) and performs within 0.02 MAE of the best Ridge configuration — for a dataset already showing weak individual feature correlations (Phase 3A.8), this near-equivalence itself suggests the regularization strength barely matters here (Section 13 explains why).

**Provisional selection: extended feature set with plain Linear Regression (mean MAE 147.54, essentially tied with the best Ridge configuration at 147.52) — chosen over Ridge specifically on the simplicity tiebreaker, since regularization strength makes almost no difference to this particular fit.** This selection uses validation results only; the 35-row test set was not consulted and must not be until a later phase's explicit test-evaluation step.

**No ML model was forced to win.** Every configuration happened to beat moving-average-3 on this data; had none done so, Section 9 would report that plainly, per the task's explicit instruction — that outcome simply did not occur here, and this report does not manufacture false modesty about a result that came out this way.

## 13. Honest Interpretation

**This is the most important section of this report, and it exists specifically to prevent the Section 9/12 numbers from being misread as "ML found a strong predictive pattern."**

Coefficient inspection (re-run directly for this report, not inferred) shows what is actually happening: for the minimal-feature Linear Regression on fold 1's training data, the fitted intercept is **1776.39 — exactly equal to the training-set mean of the target** — and the fitted slope, converted back to original units, is only about **₹0.078 of predicted-price change per ₹1 of `lag_1`**. In other words, **the model's predictions barely move away from the training-period average price, regardless of what the most recent price actually was.** Concretely, for fold 1's validation block, `lag_1` (what persistence would predict) ranged from ₹1500 to ₹2300, while the fitted Linear Regression's predictions only ranged from about ₹1755 to ₹1818 — a nearly flat line hovering around the training mean.

**Why does a nearly-flat, mean-hugging predictor beat persistence and moving-average-3 here?** Because Phase 3A.8 already established that this series has very weak short-lag autocorrelation (`lag_1`↔target correlation ≈ 0.049). On a series where the next value has little real relationship to the last value, **"predict something close to the recent average" is a statistically sound strategy that dampens noise, while "predict exactly the last value" (persistence) amplifies it.** Moving-average-3 sits in between — it smooths over 3 points, which is better than persistence's zero smoothing but less smoothing than a regression whose fitted slope is nearly zero. This is a well-understood statistical phenomenon (regression toward the mean), not evidence that the model has discovered a meaningful, exploitable price-forecasting pattern.

**The extended feature set's better result (147.52 vs. minimal's 168.46) is not purely a mean-hugging effect** — re-inspecting the extended Ridge model's coefficients shows `lag_3` (+22.7 in standardized units) and `rolling_mean_3` (+22.0) carry real, non-trivial weight, consistent with Phase 3A.8's finding that `lag_3` was the most target-correlated individual lag (0.218). **This part of the improvement is more genuinely attributable to informative features, not just averaging.** However, the same inspection also shows a `day_of_week = Sunday` coefficient of **+73.16** — the single largest coefficient in the model — estimated from roughly 23 Sunday observations in a 105-row training fold. This is exactly the kind of small-sample coefficient this report will not present as a confirmed effect: it was not independently validated against target correlation in Phase 3A.8, and a coefficient this large from this few examples should be treated as **plausibly noisy, not a demonstrated Sunday market effect**, until checked more rigorously.

**Stated as plainly as possible: this phase's result is real (the MAE numbers are not fabricated or cherry-picked), but the honest interpretation is "simple regression-to-the-mean and a couple of mildly informative lags beat two naive baselines on a short, noisy, district-level-proxy series" — not "we have found a reliable potato price forecasting model." The gap between those two claims matters, and this report deliberately does not blur it.**

## 14. Limitations

- **All results are computed on only 35 validation rows across 5 folds** (7 per fold) — the fold-to-fold MAE variability is large (e.g., extended/Ridge(α=1.0) ranges from 88.09 to 244.64 across its 5 folds), and a mean computed from this few points, while not fabricated, should not be treated as a precise, low-variance estimate of true future performance.
- **The near-identical performance across all four Ridge/Linear-Regression configurations** (147.52–147.77 for extended, 168.46–168.66 for minimal) suggests the regularization-strength choice barely matters for this particular fit — this itself is informative (Section 13) but means this phase cannot claim to have found a meaningfully "tuned" regularization strength, only that a small range was checked and made little difference.
- **The `day_of_week = Sunday` coefficient (Section 13) is flagged, not resolved** — this phase does not have the scope to re-run a dedicated day-of-week correlation check (that would be feature-analysis work belonging to Phase 3A.8's scope, already closed), so this remains an open caution for whoever next examines this feature set closely.
- **Everything here describes Hyderabad district-level proxy data over roughly 6 months of one year** — no claim in this report extends to Bowenpally-specific prices, to a different season, or to a different year.
- **The final 35-row test set has still never been evaluated by anything in this project** — the provisional selection in Section 12 is exactly that: provisional, pending a single, final, honest test evaluation in a later phase.

## 15. Recommendation for the Next Phase

Phase 4B (or equivalent) should take the provisional selection from Section 12 — **extended feature set, plain Linear Regression** (with Ridge(α=1.0) noted as an essentially equivalent alternative) — freeze it as the single chosen configuration with no further tuning, and evaluate it **exactly once** against the untouched 35-row test partition (rows [140:175] of the common window), reporting the test MAE/RMSE alongside the same statistic for moving-average-3 computed on that same test range, so the provisional validation-based finding in this report can be honestly checked against genuinely unseen data. The day-of-week coefficient concern (Section 13) should be noted in that phase's write-up as an open item, not re-investigated mid-stream in a way that would constitute additional model tuning after seeing test-adjacent information. Tomato remains out of scope.
