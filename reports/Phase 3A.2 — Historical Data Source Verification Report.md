# Phase 3A.2 — Historical Data Acquisition: Verification Report

**Date of investigation:** 2026-09-13
**Scope:** Acquire and verify historical mandi price data for Telangana — Tomato, Onion, Potato — suitable for ML time-series/trend-classification experimentation (per Phase 3A.1's selected candidate).
**Rule followed throughout:** no endpoint was guessed, no data point was fabricated or simulated. Every claim below is either a direct, reproducible HTTP result (logged with status code and timing) or explicitly marked as unconfirmed.

**Reproducibility:** every result in this report can be regenerated by running `scripts/phase3a2_ceda_data_probe.py` from the project root. The raw, unmodified server responses are saved under `data/raw/` (see Section 5).

## 3. CEDA Portal — Investigation Method

The CEDA Agri-Market Data portal (`https://agmarknet.ceda.ashoka.edu.in/`) hangs when loaded in a browser. Rather than guess at an API, its behavior was inspected programmatically:

1. Fetched the portal's HTML (`curl`) — confirmed it is a Next.js single-page application; the initial HTML carries almost no content, only script tags.
2. Downloaded every linked JavaScript chunk (`_next/static/chunks/*.js`, ~2.4 MB total) and searched them as plain text for URL literals, `fetch(...)` calls, and `NEXT_PUBLIC_*` environment-variable usage.
3. This surfaced two categories of endpoint:
   - **Auth/mailing-list endpoints** on `api.ceda.ashoka.edu.in` (`/v1/auth/portal/*`, `/v1/sedp/*`) — used for a gated bulk-download feature (OTP-based login), not investigated further as they are unrelated to querying price data directly.
   - **Same-origin data API** on `agmarknet.ceda.ashoka.edu.in` itself: `/api/states`, `/api/commodities`, `/api/districts?state_id=`, and POST `/api/prices` / `/api/quantities`, found by locating the exact `fetch("/api/...")` call sites and the object literal built for the POST body (`state_id, commodity_id, district_id, calculation_type, start_date, end_date`).
   - The `calculation_type` field's valid values were read directly from the UI's own option list in the bundle: `{id:"d",name:"Daily"}, {id:"m",name:"Monthly"}, {id:"y",name:"Yearly"}` — i.e. **daily granularity is a real, supported option**, not an assumption.
4. Every endpoint below was then called for real over HTTPS. None of the IDs used (state, district, commodity) were guessed — each was taken from the corresponding reference endpoint's actual response before being used in a query.

## 6. Test Results — Telangana, Tomato/Onion/Potato, Daily Granularity

Test query shape (identical for all three commodities): `POST /api/prices` with `state_id=36, district_id=536, calculation_type="d", start_date="2025-09-01", end_date="2025-09-07"`, commodity_id swapped per test. Each commodity was retried up to 3 times by the script before being marked failed — this is the full, unfiltered log:

| Commodity | Attempt 1 | Attempt 2 | Attempt 3 | Outcome |
|---|---|---|---|---|
| Tomato | 504 (60.1s) | 504 (60.1s) | **200 (10.2s)** | 🟢 Succeeded on 3rd attempt |
| Onion | 504 (60.2s) | 500 (25.2s) | 504 (60.4s) | 🔴 **Failed on all 3 attempts** |
| Potato | 504 (60.1s) | 504 (60.2s) | **200 (47.7s)** | 🟢 Succeeded on 3rd attempt, close to the ~60s gateway timeout |

(504 = nginx Gateway Time-out at ~60s; 500 = backend returned `{"error":"Error accessing the prices from the database"}`.)

**This is not an isolated fluke.** Manual testing earlier in this session, independent of the script, produced the same qualitative pattern across ~9 separate calls: Tomato and Potato each eventually returned real data (once each, on different attempts), while Onion failed every single time — including when tested at monthly granularity, at state level (no district filter), and with a shorter 3-day window. The reference endpoints (`/api/states`, `/api/commodities`, `/api/districts`) were fast and reliable (under 1 second) in every attempt in the automated run, though one manual attempt on `/api/states` earlier also returned a transient 500.

**Interpretation, stated plainly:** the CEDA backend is a real, functioning system with a real database behind `/api/prices` — it is not a dead or fake endpoint — but it is **operationally unreliable under this phase's testing**: reference/metadata endpoints are fast and stable, while the actual price-history query intermittently times out or errors, independent of date-range size or aggregation level. This is consistent with, and explains, the "portal stuck loading" symptom observed in the browser before this investigation began. Onion's 0-for-7 failure rate across every variation tried is a specific, reproducible weak point of this backend for this commodity — not something this report can currently explain from the outside (no error detail beyond the generic message was returned), and it should not be assumed fixed without re-testing.

## 8. Daily vs. Monthly Availability

**Daily granularity is real and was successfully retrieved** for two of the three target commodities (Tomato, Potato) — this is not a monthly-only source. `calculation_type="d"` returned one record per calendar day with no gaps in the 7-day window tested. This is a materially better result than data.gov.in's single-snapshot dataset (Section 2).

What remains **unconfirmed, not assumed**, because it could not be tested within this phase's reliability constraints:
- How far back daily history actually extends. A test against an older window (2020-01-01 to 2020-01-07) timed out (504) before returning any answer — this is a genuine "don't know," not evidence either way about historical depth.
- Whether a longer, continuous daily window (e.g., 90+ days, needed for a real train/test split) can be retrieved at all without hitting the same timeout pattern seen even on a 7-day window.
- Whether Onion's failures are permanent or transient — they were 100% reproducible in this session but the backend showed enough general flakiness (Tomato/Potato needing 3 attempts each) that a different day's testing could plausibly reverse this.

## 9. Overall Verdict

| Question | Answer |
|---|---|
| Does data.gov.in's current dataset support historical ML work? | 🔴 No — confirmed single-date snapshot (Section 2) |
| Does CEDA expose real, non-guessed API endpoints? | 🟢 Yes — recovered directly from the portal's own client code (Section 3) |
| Is daily (not just monthly) historical data available via CEDA? | 🟢 Yes, demonstrated for Tomato and Potato at Telangana/Hyderabad (Section 7) |
| Is CEDA's API reliable enough to bulk-acquire a full training dataset right now? | 🔴 No — Onion failed 7/7 times; Tomato and Potato each needed 3 attempts for one 7-day window (Section 6) |
| Is there real historical price data for Telangana Tomato/Onion/Potato, full stop? | 🟡 Partially confirmed — yes for Tomato and Potato (small verified sample); not yet demonstrated for Onion despite repeated real attempts |

**This phase does not recommend proceeding to bulk data acquisition from CEDA yet.** The samples in Section 7 prove the data *exists* and is *real*, which is a genuine advance over Section 2's finding — but the reliability pattern in Section 6 means a script that requests, say, a year of daily history for three commodities across two mandis (Phase 3A.1's actual scope) would very likely fail on a large fraction of its requests, and Onion specifically failed every single time it was tried by any method. Treating today's two small successes as proof that full acquisition is feasible would overstate what was actually observed.

## 10. Recommended Next Steps

1. **Re-test CEDA at a different time.** Today's failure pattern may reflect a temporary load or database issue on CEDA's side rather than a permanent limitation — the fact that reference endpoints (`/api/states`, `/api/commodities`, `/api/districts`) were fast and reliable while only `/api/prices` misbehaved suggests a specific backend query path issue, not a systemic outage. Re-running `scripts/phase3a2_ceda_data_probe.py` on a later date is the cheapest way to check this.
2. **If CEDA remains unreliable, investigate the official Agmarknet portal's own historical report tool** (`agmarknet.gov.in`, noted but not tested in Phase 3A.1, Section 6) as the next candidate — it is the primary source CEDA itself republishes, and may expose a more stable date-range query mechanism (e.g., a CSV export by commodity/date-range) worth probing with the same no-guessing discipline used in this phase.
3. **Do not lock the ML pipeline to CEDA yet.** Phase 3A.1's contingency — that a genuine data-sufficiency problem should be reported honestly rather than papered over (Phase 3A.1, Section 21) — applies here: today's evidence is "promising but not yet sufficient," not "ready."
4. **If CEDA access improves**, the immediate next check should be pulling a much longer continuous daily window (e.g., 6–12 months) for all three commodities to test for the gap frequency and per-series depth Phase 3A.1 flagged as the open question (Section 7.7/19 there) — this report deliberately stops short of that pull because the reliability findings above mean a large pull attempted today would mostly document timeouts, not price data.
