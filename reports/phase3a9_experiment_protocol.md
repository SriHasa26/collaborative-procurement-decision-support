# Phase 3A.9 — ML Experiment Protocol and Baseline Design

**Date:** 2026-09-13
**Scope:** Define and implement the experiment infrastructure (chronological split, expanding-window validation, final-test policy) and run only the two mandatory non-ML baselines through it. No complex model (Random Forest, XGBoost, neural network, or otherwise) is implemented or trained in this phase.
**Rule followed throughout:** every number below comes from actually running `scripts/phase3a9_experiment_protocol.py` against the real Phase 3A.8 feature files. No raw file, no processed dataset, and no prior report was modified.
**Reproducibility:** every result can be regenerated by running `scripts/phase3a9_experiment_protocol.py` from the project root.

---

## 1. Phase Objective

Phase 3A.8 built two feature tables and flagged a real, honest concern: `lag_1`'s correlation with the target is only 0.049, so predictive temporal dependence must not be assumed. This phase does not resolve that question — it builds the rigorous, leakage-safe experimental scaffold (splits, folds, baselines, evaluation rules, and a strict final-test policy) that a future modeling phase will need in order to answer it honestly. Whatever a future model reports will only be trustworthy if this scaffold is right, so it is built and tested here, on baselines alone, before anything more complex touches it.

| File | Rows | Feature date range |

## 3. Dataset Split Decision

**The two files were not compared as if they had the same rows.** Extended has 175 rows because it needs 2 extra prior observations (for `lag_3`/the rolling window) before its first row can exist. This was **verified empirically, not assumed**: every one of extended's 175 rows was checked directly against minimal's rows, offset by 2, and found identical in both date and target value (0 mismatches). This confirms **extended's full 175-row range is exactly a sub-range of minimal's 177 rows** — specifically, minimal's rows 3–177.

**This is the basis for Task 11's fairness policy (Section 10): the common evaluation window is defined as these 175 shared rows**, not as "175 rows from one file and 177 from the other, compared as if equivalent."

**On the 60/20/20 question:** Phase 3A.7 proposed roughly 60/20/20 as an explicitly unvalidated placeholder. Applied to the actual common-window size (n=175), 60/20/20 computes to **exactly 105/35/35** — a clean, whole-number division with zero rounding ambiguity. This phase adopts that split **because it was checked against the real row count and found to divide cleanly**, not because 60/20/20 was accepted by default. Had 175 not divided this cleanly, this phase would have adjusted the ratio rather than force a fractional row boundary — the script's `define_split()` computes boundaries from `n` directly rather than hardcoding row numbers, so this check is reproducible for any future dataset size, not just this one.

## 4. Chronological Split Boundaries

Computed directly from the common 175-row window, in feature-date order (the date at which the *features* are observed, i.e. $t$, not the target date $t+1$):

| Partition | Row indices (0-indexed) | Row count | Feature-date range |
|---|---|---|---|
| **Train** | [0:105] | 105 | 2025-03-07 to 2025-06-24 |
| **Validation** | [105:140] | 35 | 2025-06-26 to 2025-08-01 |
| **Test (untouched)** | [140:175] | 35 | 2025-08-02 to 2025-09-06 |

**No row was shuffled to produce these boundaries** — they are a straight chronological cut, verified by the script's own ordering check before the split was computed.

## 5. Expanding-Window Validation Design

**Fold size: 7 rows. Number of folds: 5** (35 validation rows ÷ 7 = exactly 5, again a clean division rather than a forced choice).

| Fold | Training range | Training rows | Validation range | Validation rows |
|---|---|---|---|---|
| 1 | [0:105] | 105 | [105:112] | 7 |
| 2 | [0:112] | 112 | [112:119] | 7 |
| 3 | [0:119] | 119 | [119:126] | 7 |
| 4 | [0:126] | 126 | [126:133] | 7 |
| 5 | [0:133] | 133 | [133:140] | 7 |

**Chronology is enforced by construction, not merely by description:** each fold's training range ends exactly where its validation range begins (`train_range = (0, fold_val_start)`), so no validation row can ever appear in that fold's training data, and no training row is ever drawn from beyond the validation block that follows it. Each successive fold's training range **expands** to absorb the previous fold's validation block (now realized, historical data) — this is standard walk-forward structure, and the numbers above show it holding exactly (105→112→119→126→133).

**Why 7-row folds, not something else:** a 35-row validation pool split into 5 folds of 7 gives enough folds (5) to see fold-to-fold variability (Task 10) without shrinking any single fold below a size that would make its MAE/RMSE meaningless (7 observations per fold is small but workable for a simple average-error statistic; fewer than ~5 would not be). This is stated as a reasoned choice, not the only possible one.

**A note on what this fold structure actually does for parameter-free baselines:** persistence and moving-average-3 have no parameters to fit, so their predictions do not literally depend on the "training" data in any fold — `lag_1` and `rolling_mean_3` are already fixed values in each row from Phase 3A.8's construction. The fold structure's value in *this* phase is (a) organizing the validation pool into 5 chronological chunks so variability across time can be reported honestly (Section 8), and (b) establishing, and testing on baselines, the exact expanding-window mechanism a future parameterized model will actually need to fit within. This is stated plainly so the fold structure is not mistaken for something that changed a parameter-free baseline's predictions.

## 6. Persistence Baseline

**Formal definition:** $\hat{y}_{t+1} = y_t$.

**Implementation:** read directly from each row's `lag_1_modal_price` feature — which, by Phase 3A.8's own construction and independently-verified alignment (that phase's Section 11), already equals the modal price at the most recent *available* observation, never a future value. No new computation was needed; this baseline is a direct reading of an already-verified column.

**Leakage check:** `lag_1_modal_price` is built from index $\le t$ only (Phase 3A.8), so $\hat{y}_{t+1}$ never uses $y_{t+1}$ or later. Verified by inheritance from Phase 3A.8's own leakage assertions, not re-derived from scratch here (no need to duplicate work already done correctly).

**Per this phase's Task 3 instruction, the test partition (Section 4) was not evaluated with this baseline** — only the 5 validation folds were (Section 8).

## 7. Moving-Average Baseline

**Window evaluated: 3 observations. No other window size was tried.**

**Formal definition:** $\hat{y}_{t+1} = \frac{1}{3}(y_t + y_{t-1} + y_{t-2})$.

**Implementation, with an explicit cross-check built in:** for the extended file, this baseline reads the already-verified `rolling_mean_3_modal_price` column (Phase 3A.8). For the minimal file — which has no rolling column — this script independently *recomputes* the same 3-point average from three consecutive rows' `lag_1_modal_price` values (each of which is itself $y_t$, $y_{t-1}$, $y_{t-2}$ by construction of consecutive rows). **Both computations were run and compared on the identical underlying observations, and produced byte-for-byte identical fold results (Section 9)** — this is a genuine, independent cross-check, not a repeated calculation dressed up as one.

**Why not a larger window:** Phase 3A.8 already reasoned that a window larger than 3 would cost more rows and smooth over the short-term volatility the target variable was chosen partly because of (Phase 3A.7). That reasoning is not repeated in full here, only reused — a second, larger moving-average baseline was not run in this phase, consistent with the task's instruction not to automatically evaluate many windows.

## 8. Evaluation Metrics

**Primary: MAE. Secondary: RMSE.** Both computed exactly as Phase 3A.7 specified — no additional metric (e.g. MAPE) was introduced, per this phase's explicit instruction not to add unnecessary metrics.

- **MAE** = mean of $|y_{t+1} - \hat{y}_{t+1}|$ over a fold's validation rows — in ₹/quintal, directly interpretable.
- **RMSE** = square root of the mean of $(y_{t+1}-\hat{y}_{t+1})^2$ — also in ₹/quintal, more sensitive to a few large errors than MAE.
- **Interpretation:** lower is better for both; a method is preferred over another only if it achieves lower MAE (primary) — RMSE is reported alongside to check whether a lower MAE is being driven by consistently smaller errors or is instead masking a few very large ones.
- **Comparison rule:** methods are compared fold-by-fold and by their mean across all 5 folds, using identical validation rows for every method compared (Section 10) — never comparing one method's performance on one set of rows against another method's performance on a different set.

## 9. Baseline Results

**Full per-fold results, exactly as produced by the script (not summarized away):**

| Fold | Val. rows | Persistence MAE | Persistence RMSE | Moving-avg-3 MAE | Moving-avg-3 RMSE |
|---|---|---|---|---|---|
| 1 | 7 | 267.86 | 393.36 | 267.86 | 293.33 |
| 2 | 7 | 310.71 | 384.17 | 255.95 | 304.19 |
| 3 | 7 | 228.57 | 253.90 | 128.57 | 138.01 |
| 4 | 7 | 200.00 | 243.85 | 178.57 | 200.94 |
| 5 | 7 | 200.00 | 259.58 | 118.25 | 180.52 |

**Mean across folds (with cross-fold standard deviation, showing variability, not hidden):**

| Method | Mean MAE | Stdev of MAE across folds | Mean RMSE | Stdev of RMSE across folds |
|---|---|---|---|---|
| **Persistence** | 241.43 | 42.65 | 306.97 | 67.04 |
| **Moving-average-3** | **189.84** | 62.39 | **223.40** | 64.89 |

**Which baseline performs best, stated honestly:** **Moving-average-3 beats persistence in every single one of the 5 folds**, on both MAE and RMSE, with no exception. Its mean MAE (189.84) is about 21% lower than persistence's (241.43). This is a real, if modest, result — it does **not** mean the series is easy to forecast (₹190/quintal average error against a target ranging ₹1,300–2,300 is still a substantial relative error, roughly 11–14% of the price level in most of the range), but it does mean the *simplest possible* smoothing already outperforms doing nothing more than repeating the last value. **Moving-average-3's fold-to-fold variability is comparable to or slightly higher than persistence's** (stdev 62.39 vs. 42.65 on MAE) — its average advantage is not uniformly larger every fold by the same margin (Fold 1 shows a tie), which is reported here rather than smoothed into a single "it's simply better" headline.

**Nothing here was hidden for looking unimpressive.** Neither baseline is good in an absolute sense; moving-average-3 is simply the better of the two available simple methods, on this data, in this window.

## 10. Feature-Set Comparison Fairness

**Policy adopted: Option A — a common evaluation period**, per Task 11's own framing. The 175-row common window (Section 3) is used identically for both file representations; no separate fold structure was built for minimal and extended.

**Direct proof this was actually enforced, not just claimed:** the script ran the identical 5-fold protocol twice — once reading features from `potato_ml_extended.csv`, once from the equivalent rows of `potato_ml_minimal.csv` — and compared the resulting mean MAE for both baselines. **The difference was exactly 0.000000 for both persistence and moving-average-3.** This is the strongest form of the fairness check the task asked for: not an assertion that the comparison *would* be fair, but a demonstration, on the actual data, that both representations of the same underlying observations produce identical baseline numbers when evaluated on the same target rows.

**What this means for a future model comparison:** when a real model is eventually fit on `potato_ml_extended.csv`'s full feature set, its performance must be compared against baselines computed over this same 175-row common window (not minimal's extra 2 leading rows, which extended structurally cannot use) — anything else would be comparing performance on different observations, which Task 5/11 both explicitly forbid.

## 11. ML Value Criteria

Defined here, before any model exists, so the bar is not adjusted after seeing a result:

1. **Mandatory minimum (statistical improvement):** a candidate model must achieve a lower mean validation MAE than **both** baselines — persistence (241.43) and moving-average-3 (189.84) — using the identical 5-fold protocol and the identical common-window rows defined above. Beating only one baseline is not sufficient.
2. **Practical improvement, distinguished from statistical improvement:** even if a model clears criterion 1, whether the margin is *practically* meaningful is a separate question this phase does not pre-answer with an invented number — e.g., a model achieving MAE=185 against moving-average-3's 189.84 is a statistical win but arguably not a practically meaningful one for a vendor-facing decision tool. **No specific ₹-value threshold for "practically meaningful" is proposed here**, per the task's explicit instruction not to invent arbitrary thresholds — that judgment should be made once real model results exist and can be discussed in concrete terms (e.g., relative to typical transport-cost savings this project's Phase 2A model computes), not decided in the abstract now.
3. **If no candidate model beats moving-average-3 (the stronger baseline) on mean validation MAE, this must be reported as a negative result, not hidden or reframed as a partial success.** This is consistent with Phase 3A.8's own flagged concern (weak lag-target correlation) — this phase does not assume that concern will be resolved favorably.

## 12. Final Test Policy

**Stated as a strict, binding rule for every future phase, not merely a description of what happened today:**

- The 35-row test partition (Section 4, rows [140:175], 2025-08-02 to 2025-09-06) was **identified and its boundaries computed, but no baseline or model prediction was evaluated against it in this phase** — confirmed directly in the script output: only the 5 validation folds were scored; the test range appears only as a printed boundary, never as an input to `evaluate_fold()`.
- The test partition must **never** influence feature selection, hyperparameter selection, or model choice — those decisions must be finalized using only the training and validation-fold results.
- The test partition may be evaluated **exactly once**, after model selection is complete, and that result must be reported as-is, whatever it shows — re-running the test evaluation to "check" a different model configuration after seeing the first test result would defeat the entire purpose of holding it out.

## 13. Final Experiment Protocol

| Element | Definition |
|---|---|
| 1. Dataset used | Potato, Hyderabad district-level (proxy), `potato_ml_minimal.csv` and `potato_ml_extended.csv`, restricted to their common 175-row window (Section 3) |
| 2. Forecasting task | One-step-ahead prediction of `modal_price_rs_quintal` at the next *available* observation, per Phase 3A.7 |
| 3. Chronological split | Train [0:105] / Validation [105:140] / Test [140:175] — 60/20/20 of n=175, verified to divide cleanly (Section 3/4) |
| 4. Expanding-window design | 5 folds of 7 validation rows each, training range strictly preceding and expanding into each successive fold (Section 5) |
| 5. Number of folds | 5 |
| 6. Baseline definitions | Persistence ($\hat{y}_{t+1}=y_t$) and moving-average-3 ($\hat{y}_{t+1}=\text{mean}(y_t,y_{t-1},y_{t-2})$) (Sections 6–7) |
| 7. Metrics | MAE (primary), RMSE (secondary) (Section 8) |
| 8. Model comparison criteria | Must beat both baselines' mean validation MAE on the identical common-window folds; statistical vs. practical improvement kept distinct (Section 11) |
| 9. Feature-set comparison policy | Common 175-row evaluation window (Option A), fairness demonstrated by a 0.000000 cross-representation MAE difference (Section 10) |
| 10. Final-test policy | 35-row chronological tail, identified but unevaluated this phase; usable exactly once, after model selection (Section 12) |
| 11. Research integrity rules | No shuffling; no future data in any training/validation range; no test-set use before model selection; baseline results reported in full including their weaknesses (Section 9); no arbitrary practical-improvement threshold invented (Section 11) |

## 14. Limitations

- **35 rows per fold-relevant partition (validation and test) is small.** A 21%-relative MAE improvement from moving-average-3 over persistence, on only 35 validation observations split into 5 folds of 7, should be read as a real but not statistically overwhelming signal — this phase does not claim more precision than a sample this size can support.
- **The 7-row fold size and 60/20/20 split ratio are reasoned choices, not the only defensible ones** — they were checked for clean divisibility against the actual row count (Section 3/5), which is a real justification, but a different, equally defensible split (e.g., fold size 5, giving 7 folds) was not tested against this one.
- **Both baselines are parameter-free**, so this phase's expanding-window "training" step did not actually exercise any fitting logic — the infrastructure is built and demonstrated to respect chronology correctly, but a future phase's first parameterized model will be the first real test of whether the "train on the expanding window, then predict" mechanism behaves correctly when there is something to fit.
- **The weak lag-target correlation flagged in Phase 3A.8 (0.049 for lag_1) is not contradicted or resolved by moving-average-3's win here** — a 3-point average can outperform naive persistence even when individual lags are weakly correlated with the target, simply by damping noise; this result does not, by itself, prove that Potato prices are meaningfully forecastable, only that mild smoothing helps a little more than no smoothing.

## 15. Recommendation for the Next Phase

Phase 3A.10 (or equivalent) should fit exactly one simple, low-complexity model (e.g., a linear regression on the extended feature set, or a shallow single-tree regressor) using the identical training range [0:105] and the identical 5-fold expanding-window validation defined here, and compare its mean validation MAE directly against persistence (241.43) and moving-average-3 (189.84) using the Section 11 criteria. The 35-row test partition must remain untouched until that model (or a small number of candidate models, chosen using only validation results) is finalized. Tomato remains out of scope. No feature or split decision made in this phase should be re-opened without a documented reason.
