# Phase 3A.4 — Historical Dataset Acquisition

**Date of acquisition:** 2026-09-13
**Scope:** Perform a controlled, polite, non-fabricated acquisition of real historical daily mandi price data for Tomato and Potato (Telangana), building on Phase 3A.2/3A.3's finding that CEDA is the primary programmatic candidate and official Agmarknet 2.0 is the authoritative but CAPTCHA-gated fallback.
**Rule followed throughout:** no data was fabricated, simulated, or silently repaired. Every number below comes from a real HTTP response, logged with its status code, or from direct inspection of the saved raw files. Failures are reported exactly as they occurred.
**Reproducibility:** every result in this report can be regenerated by running `scripts/phase3a4_ceda_acquisition.py` from the project root (results will vary with CEDA's live reliability at the time of running — this is expected and discussed in Section 9).

---

## 1. Objective

Acquire a real, reproducible historical dataset — not a proof-of-concept sample — for Tomato and Potato at the geographic level CEDA actually supports, using controlled request chunks, limited retries, and honest logging of every success and failure. Onion was explicitly out of scope for this phase (Phase 3A.2/3A.3 already showed it fails reliably on CEDA) and was not attempted, so as not to spend request budget on a commodity already known to fail.

## 2. Geographic Granularity Decision

**Classification: B — District-level.**

**Evidence, not assumption:**
1. Every record CEDA's `/api/prices` endpoint has ever returned (Phase 3A.2, Phase 3A.3, and this phase) carries the fields `t, cmdty, district_id, district, p_min, p_max, p_modal` — there is no market, mandi, or APMC field anywhere in the schema.
2. CEDA's own client-side filter UI (inspected directly from its JavaScript bundle in Phase 3A.2/3A.3) exposes only a state filter, a commodity filter, and a **district** filter — there is no market/mandi selector anywhere in the interface, and the request body itself only accepts `state_id`, `commodity_id`, `district_id`. A mandi-level query is not merely unavailable today — it is not a parameter this API supports at all.

**Justification for use despite the mismatch with this project's original scope:** Phase 1B/1C fixed this project's study mandis as Bowenpally APMC and Gaddiannaram APMC, both of which sit inside Hyderabad district. Since CEDA cannot resolve below district level, **Hyderabad district-level data is used here as an explicit geographic proxy for those two mandis, not as an equivalent replacement.** This is a real limitation: a district-level daily price is a market-weighted or averaged figure across every reporting mandi in Hyderabad district (evidenced by the non-integer `p_min`/`p_max`/`p_modal` values, e.g. `1266.6666666666667` — a value that can only arise from averaging, not from a single mandi's raw reported price), so it will smooth over any price divergence between Bowenpally and Gaddiannaram specifically. This is stated plainly, not hidden: **any ML model trained on this data is modeling Hyderabad-district-level price trend, not Bowenpally- or Gaddiannaram-specific price trend**, and that distinction must be carried into Phase 3A.1's model documentation when training begins.

No geographic levels are mixed within a single acquired series: every file produced this phase is Hyderabad-district-only, for a single commodity.

## 3. Acquisition Configuration

| Setting | Value |
|---|---|
| Commodities attempted | Tomato (`commodity_id=78`), Potato (`commodity_id=24`) |
| Commodity explicitly not attempted | Onion — out of scope per this phase's instructions |
| State | Telangana (`state_id=36`, CEDA's own numbering) |
| Geographic level | District (`district_id=536`, Hyderabad) — see Section 2 |
| Calculation type | Daily (`calculation_type="d"`) |
| Chunk plan | 1 test chunk (7 days: 2025-09-01 to 2025-09-07) + 6 chunks of 30 days each, walking backward from 2025-08-31 to 2025-03-05 |
| Max retries per chunk | 3, with exponential backoff (10s, then 20s) between attempts |
| Delay between chunks | 6 seconds, taken regardless of outcome |
| Stop condition | 2 consecutive fully-failed chunks (all 3 retries exhausted) for a commodity halts further chunks for that commodity |
| Request timeout | 65 seconds per attempt |

This configuration was chosen specifically to avoid hammering CEDA: chunks are requested sequentially with mandatory delays, retries are capped and backed off, and a demonstrated failure pattern stops further attempts rather than being retried indefinitely.

## 7. Data Source Status

**CEDA classified as: Partially successful.**

This is not rounded up to "successful" and not rounded down to "insufficient" — it is reported exactly as the evidence shows: CEDA delivered a genuinely usable ~6-month, near-daily historical series for one of the two priority commodities (Potato), satisfying every one of Phase 3A.3's minimum requirements (daily granularity, chronological, single consistent geography, 178 records well above the 90-day/observation floor, a documented and reproducible acquisition method, raw responses preserved unmodified) — while completely failing, within a controlled and honest retry budget, for the other priority commodity (Tomato). A source that fully succeeds for one required commodity and fully fails for another, on the same day, using the same script, against the same backend, is "partially successful" by definition, not "successful" (which would require both) and not "insufficient" (which would require neither).

## 9. Risks and Limitations

- **Today's result is a snapshot of today's CEDA reliability, not a permanent verdict on Tomato.** The same script, run on a different day, might succeed for Tomato and fail for Potato — Phase 3A.2 and 3A.3 both already showed this exact reversal pattern (Tomato succeeded then, Potato succeeded then; today Potato succeeded and Tomato did not). Tomato should be retried on a later date before being treated as permanently unacquirable from CEDA.
- **District-level data is a geographic proxy, not the mandi-level data this project originally specified** (Section 2). Any model trained on this Potato series is describing Hyderabad-district price behavior, which may diverge from Bowenpally- or Gaddiannaram-specific behavior in ways this dataset cannot detect.
- **9 missing dates (4.8%) remain unfilled in the raw Potato data**, as instructed. Any future preprocessing step must handle this explicitly (e.g., documented interpolation or exclusion) rather than assuming a clean daily series.
- **The dramatic speed change within the Potato run (53s/25s down to ~0.3s) is unexplained.** It may indicate server-side caching that would not hold for a different, not-yet-requested date range, so future acquisition attempts should not assume sub-second responses are the norm.
- **The 7 raw Potato files are not concatenated or re-sorted into one series.** They remain as 7 separate, unmodified JSON files exactly as returned, per the no-preprocessing rule — assembling them into one ascending-chronological-order dataset is deliberately left for a future, explicitly-labeled processing step, not done silently here.
- **The manual Tomato fallback (Section 8) has not been executed.** Until a human performs it, this project has zero Tomato historical data of any kind beyond the single unusable data.gov.in snapshot (Phase 3A.2).

## 10. Final Verdict

**Potato: real, verified ~6-month daily historical dataset acquired from CEDA at Hyderabad district level — usable as a starting point for ML experimentation, with the district-level proxy limitation (Section 2) and the 9 missing dates (Section 5) carried forward as documented constraints, not hidden ones.**

**Tomato: CEDA acquisition failed completely today, within a controlled and honest retry budget, and was correctly halted rather than hammered further. A manual fallback via official Agmarknet 2.0 is specified (Section 8) and required before Tomato can be included in the same ML component as Potato.**

**Onion: out of scope this phase, unchanged from Phase 3A.2/3A.3's finding that it fails reliably on CEDA.**

This phase does not declare CEDA a fully solved data source, and does not declare it worthless — it reports, with evidence, that it delivered exactly one of two required commodities today, and specifies precisely what a human needs to do to close the gap for the other, without fabricating anything in the meantime.
